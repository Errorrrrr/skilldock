# 统一管理目标、实现差距与简化建议

> 本文保留优化前的目标分析。用户随后要求「优化一版」，已实施范围与保留边界见[统一管理优化说明](management-optimization-2026-09-25.md)；本文中的候选方案不等同于全部已实现。

日期：2026-09-25。源码基线：`8798224`，0.3.0。本文是目标分析和设计建议，不代表用户已决定删除备份、迁移实体或授权实施重构。

## 用户明确的目标

1. 所有受管 Skill 的实体进入一个统一目录；工具通过软链接使用。
2. 可以从 Skill 网站、Git 或本地添加内容，再分发给常用工具目录。
3. 能归集工具目录中已经存在的 Skill。
4. 支持由多个 Skill 组成的功能或工作流，既可能是本地文件夹，也可能是 Git 项目。
5. 正确处理重名，统一目录中的文件清晰、易读。
6. 评估备份是否必要、取消备份能否简化实现。用户尚未决定取消。

这里将“统一目录”理解为唯一受管内容所在位置，而非只在统一目录放一个指向外部实体的入口。添加本地内容不等于自动删除用户的原始项目；只有明确执行归集接管时才替换原位置。工具内置、插件托管内容应明确列为外部管理，不强行搬走。

## 总体判断

导入适配器、工具目录发现、软链分发、包结构保存、预设和文件事务均已具备。主要差距是：本地直接引用与统一收录并存；扫描目录与包边界混用；名称、内容身份和安装名称未完全分离；不同入口存在流程差异；备份、旧版本兼容和日志管理叠加了复杂度。

上一轮入口缺陷的详细证据仍以 [功能检查报告](functional-audit-2026-09-25.md) 为准，本文件不重复维护那些缺陷的完整说明。

## 与目标的差距及漏洞

### A. 本地来源没有真正纳入统一实体目录

`save_local_source` 创建 `external_path` 记录，实体留在原目录；统一目录的名称入口及目标链接最终都可能指向库外。原目录移动或删除会使安装失效，本地修改未经更新确认就生效。

证据：[local_sources.rs](/Users/zxx/dev/skilldock/crates/skilldock-core/src/local_sources.rs:107)、[实体路径解析](/Users/zxx/dev/skilldock/crates/skilldock-core/src/lib.rs:69)。

建议：本地、Git、网站统一经过“准备内容 → 预览 → 收录当前内容 → 分发”。本地路径作为来源记录，用于手动再次同步。取消普通流程中的直接引用模式；若日后确有开发需求，再作为明确的开发模式，而非默认来源类型。现有外部引用须预览后迁入，不能直接删配置或切断链接。

### B. 归集冲突预览没有接通真实库判定

原生 `scan_many` 仅扫描文件系统并按物理路径去重，不读取库中的名称、来源和内容。归集页面中针对 `same/conflict` 的分支因此不能完成承诺的同名处理；提交也只传目录、选中路径与是否接管。实际重名通常在事务末尾才被自动加后缀。

证据：[scan_many](/Users/zxx/dev/skilldock/crates/skilldock-core/src/files.rs:623)、[归集扫描和提交](/Users/zxx/dev/skilldock/src/pages/ImportPage.vue:306)、[冲突控件](/Users/zxx/dev/skilldock/src/pages/ImportPage.vue:784)。

建议：后端提供统一导入计划，覆盖跨扫描目录及现有库的重复；返回内容等价、差异、包边界、最终名称、原目录如何处理、受影响目标。确认动作提交计划版本与明确选择，并重新校验磁盘内容。

### C. 同一份 Skill 的去重被扫描根影响

归集时对整个扫描根创建快照；Skill 身份比较使用整包摘要与成员相对路径。假设工具甲有 `A+B`，工具乙有 `A+C`，即使两份 A 本身一致，整根摘要不同也不会合并。仅选择 A 时，底层仍可能保存扫描根中的其他内容。

证据：[整根快照](/Users/zxx/dev/skilldock/crates/skilldock-core/src/operations.rs:873)、[完整包与成员路径比较](/Users/zxx/dev/skilldock/crates/skilldock-core/src/single_content.rs:4)。

这是保守保留依赖的实现，却不完全适合散装工具目录归集。不能简单改成只比较 SKILL.md，甚至仅比较 Skill 子目录也不总够：A 可能依赖包根的 shared 文件。

建议区分：

- 独立 Skill：比较其完整目录及确认的依赖范围。
- 真正的工作流包：保存原始相对结构，以包为内容变更单位，成员以包身份与相对路径识别。
- 工具分发目录：属于安装位置，不能默认把它整体认定为一个共同来源包。

对无法确认依赖范围的条目保留独立并提示，而不强行合并。

### D. 名称后缀只解决了管理目录占用

同名记录自动增加 `--短ID`，但不修改 SKILL.md 中的 name，也不更新工作流中对名字的引用。本地引用分发取原目录 basename，快照分发取库内名称，导入顺序可能决定是触发同路径冲突还是用后缀并存。不能据此保证目标 Agent 不会遇到逻辑名称歧义；具体加载表现取决于工具。

证据：[记录改名](/Users/zxx/dev/skilldock/crates/skilldock-core/src/single_content.rs:138)、[分发命名](/Users/zxx/dev/skilldock/crates/skilldock-core/src/operations.rs:328)。

建议分别记录内容身份、SKILL.md 声明名、可读展示名和安装名：

- 相同内容与依赖可复用，保留收录来源。
- 同名不同内容允许在库中保留候选，以可读来源名区分。
- 同一目标默认只启用一个相同声明名的实现；明确选择替换，并核对预设引用。
- 不通过随机后缀隐式认定两个同名 Skill 可共同工作。重命名需考虑目标工具规则及包内引用，不能默认改用户内容。

### E. 工作流已有物理包支持，但逻辑需要收敛

Git 集合与本地包已经保留共享资源和成员相对路径，这部分应保留。预设用于组合选中成员并整体分发，能覆盖用户说的“一批 Skill 实现一个功能”。无需因此新增工作流执行引擎。

应明确：包保存真实目录结构和共享资源，预设只保存成员组合及分发引用，不再引入第二套内容副本或独立版本锁。部分成员与共享依赖需保留关联，来源删除成员时明确审阅。

当前依赖检查集中于部分 Python 环境模式，不能称为通用运行环境验证；不应因包中无关、未选成员的环境问题就笼统阻断全部独立成员。适配范围须明确。

### F. 目录可读性目前主要依靠入口软链

默认模式下用户看到名称入口，但实体在隐藏的 `.skilldock/objects/<摘要>/tree`。这能保留包结构和验证能力，不能等同于“每个顶层名称目录都是独立实体”。复制整个统一目录时，只复制可见入口不够；直接手工修改快照后，再分发还可能被内容校验阻止。

建议第一步保留已验证的对象存储，明确展示入口、实际包位置和修改后重新收录流程，不为目录美观直接重写全部存储。若后续需要可手工浏览和维护的实体布局，可评估：

```text
SkillDock/
  skills/                  # 按可读名称浏览的成员入口
    code-review -> ../packages/code-review/
    storyboard -> ../packages/short-drama/skills/storyboard/
  packages/                # 唯一当前实体，保留原始相对结构
    code-review/SKILL.md
    short-drama/
      skills/
      shared/
  .skilldock/               # 状态、临时事务及受控恢复内容
```

这是候选布局，未批准迁移。实体地址稳定不代表可以原地覆盖半个包；整包替换仍需临时区、事务和恢复。运行中 Agent 对路径的使用方式也需验证。

## 备份究竟保留了什么

| 机制 | 当前行为 | 是否可以简化 |
| --- | --- | --- |
| 归集原目录备份 | 默认最近 3 批，配置允许 1–100；每批可能有多个目录，原件留在原工具目录旁 | 可取消成功后的长期留存，保留操作中的临时原件 |
| 来源更新恢复 | 每来源最多一份上次内容，撤销按来源包处理 | 可保留为隐藏的单次撤销，或明确取消撤销能力 |
| 文件事务恢复 | 记录变更前后状态、链接变更，失败回滚／中断恢复 | 必须保留或用等价的安全机制替代 |
| 统一库迁移暂存 | 新位置校验并启用后清理旧位置 | 仍需保留完成前的恢复路径 |

证据：[默认留存](/Users/zxx/dev/skilldock/crates/skilldock-core/src/model.rs:217)、[不允许设置为 0](/Users/zxx/dev/skilldock/crates/skilldock-core/src/operations.rs:1547)、[更新恢复记录](/Users/zxx/dev/skilldock/crates/skilldock-core/src/single_content.rs:188)。这些是代码规则，不代表正在运行的实例实际存在同样数量的备份。

“每来源一份”不是全库一份；归集原件、当前对象、恢复对象、外部引用保护和异常残留也不是同一个计数。它们主要是撤销与恢复机制，不是磁盘损坏后的独立全库灾难备份。

## 是否应取消备份

建议取消完整的长期归集备份管理产品面，保留内部事务恢复；若保留自动应用更新，建议继续保留每包一次隐藏的更新恢复。

归集可以改为：复制到统一库临时区并验证 → 原目录临时改名 → 创建并验证链接 → 提交状态 → 清理已无用途的临时原件。失败或崩溃时恢复；发现外部修改、引用或清理失败时保留并给出待处理状态，不强求磁盘立即零残留。

日后退出管理可以提供“将当前内容还原为实体目录”，而不是恢复多个月前的原始内容。此功能也是建议，当前未据此实施。对有共享依赖的包需要完整还原结构，不能简单复制单个 Skill 子目录。

两种更新策略的选择：

| 方案 | 复杂度与能力 |
| --- | --- |
| 无长期恢复内容 | 最简；提交后即清理不再引用的旧内容，更新完成后不能撤销。建议默认人工审阅更新；上游仍可下载不等于本地修改或旧版本一定能恢复 |
| 每包一次隐藏恢复 | 多维护一个旧内容引用及撤销入口，能处理“文件更新成功但实际不好用”；更适合自动更新与整包工作流 |

完全不保留操作期间的旧内容不可取。例如跨盘复制成功前删原文件、建链失败后无原件、多个目标只切换一半，均不能靠“文件操作简单”解决。无需把这种临时保护暴露成备份中心。

现有 ContentBackup 模块并非主要复杂度来源。取消长期归集批次恢复，比只去掉一次更新恢复更能减少跨历史状态的关系协调；但现有备份不能通过直接删目录来退场，需要检查引用和迁移。

## 不取消备份也需要处理的日志问题

事务日志保存完整 before/after Snapshot，Snapshot 又含任务历史；每次读取状态都会反序列化所有历史日志，旧日志 JSON 损坏会让整个 snapshot 返回错误。取消备份界面不会解决这一点。

应把进行中的恢复日志与完成后的精简操作历史分离，保留引用证据与需要的恢复信息，完成日志压缩或索引化；读取已完成日志异常不应阻断整个库，但未完成事务仍需严格阻止不安全写入。

证据：[完整状态日志](/Users/zxx/dev/skilldock/crates/skilldock-core/src/lib.rs:383)、[全量历史读取](/Users/zxx/dev/skilldock/crates/skilldock-core/src/lib.rs:189)。这是静态确认的读取及失败路径，未进行性能基准。

## 建议实施顺序与验收

1. 收敛为所有受管实体入库，来源只负责内容输入；保留包、预设、工具目标这几个明确概念。
2. 实现统一导入计划，修正归集冲突预览，区分独立 Skill 和真实包；核对重名声明与目标选择。
3. 修复先前报告中的安装后续动作、部分失败提示、预设同步及异常取消流程。
4. 精简长期归集备份；决定是否保留一次隐藏更新恢复，再处理历史数据迁移和日志压缩。
5. 完成以下隔离验收后才动真实库：所有受管实体位于统一根内；重复归集不增加不必要副本；同名不同内容必须预览选择；整包共享依赖仍可访问；任意失败点不会丢失原件；每个已确认目标都正确链接；连续更新后无引用缓存和对象可有界回收。
